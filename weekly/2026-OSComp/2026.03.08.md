### 开发日志📔

#### 任务清单（共 8 个任务）

###### 任务 1：GDB MI2 输出解析器

**现状**：`gdbAdapter.ts` 把 GDB stdout 全部丢到 `process.stderr`（仅供日志），完全没有解析。

**工作内容**：

- 编写 MI2 输出行解析器，能识别以下消息类型：
	- `*stopped` (异步执行记录 — 断点/信号/单步完成)
	- `*running` (程序恢复执行)
	- `^done` / `^error` / `^running` (命令同步响应)
	- `~"..."` (console stream, GDB 文本输出)
	- `=thread-created` / `=thread-exited` / `=library-loaded` 等通知
- 实现行缓冲（MI2 输出是按行分隔的）
- 为每个 MI2 命令建立 token → callback 映射（MI2 支持给命令加前缀数字 token）

**完成标志**：GDB 输出能被结构化解析为类型化对象，日志中可以看到解析结果。DA 仍可启动/关闭。

------

###### 任务 2：DAP `configurationDone` + 自动 `run`

**现状**：`launch` 只启动 GDB 进程，没有执行 `-exec-run`，程序不会真正运行。

**工作内容**：

- 处理 `configurationDone` 请求 → 向 GDB 发送 `-exec-run --start`（或 `-exec-run`）
- 在 GDB 返回 `*stopped` 时，向 VS Code 发送 DAP `stopped` 事件
- 在 GDB 返回 `*running` 时，向 VS Code 发送 DAP `continued` 事件

**完成标志**：按 F5 启动调试后，程序能实际运行起来，命中入口断点时 VS Code 能显示"已暂停"状态。

------

###### 任务 3：`threads` + `stackTrace` 请求

**现状**：完全没有实现。VS Code 无法获取线程列表和调用栈。

**工作内容**：

- `threads` → 发送 `-thread-info`，解析响应，返回 DAP `Thread[]`
- `stackTrace` → 发送 `-stack-list-frames`，解析响应，返回 DAP `StackFrame[]`（包含 source 定位信息）
- 维护 frameId 映射（DAP frameId → GDB frame level + threadId）

**完成标志**：暂停时 VS Code 左侧能看到线程列表和调用栈，点击某帧能跳转到源码位置。

------

###### 任务 4：`scopes` + `variables` 请求

**现状**：完全没有实现。暂停时变量面板为空。

**工作内容**：

- `scopes` → 基于 frameId，返回 `Locals` / `Arguments` 两个 scope
- `variables` → 发送 `-stack-list-variables --all-values` 或 `-stack-list-locals`，解析 MI2 响应
- 处理结构体/枚举等复合类型的展开（`variablesReference > 0` 时发 `-var-create` / `-var-list-children`）

**完成标志**：暂停时 VS Code 变量面板能正确显示当前帧的局部变量和参数。

------

###### 任务 5：执行控制（continue / next / stepIn / stepOut / pause）

**现状**：工具栏上的执行控制按钮全部不工作。

**工作内容**：

- `continue` → `-exec-continue`
- `next` → `-exec-next`
- `stepIn` → `-exec-step`
- `stepOut` → `-exec-finish`
- `pause` → `-exec-interrupt`
- 每个命令发出后，等 GDB 的 `*stopped` / `*running` 响应，再发对应 DAP 事件

**完成标志**：调试工具栏全部按钮可用，单步/继续/暂停行为正确。

------

###### 任务 6：`setBreakpoints` 请求（用户断点）

**现状**：无法通过 VS Code 界面设置断点。

**工作内容**：

- 处理 `setBreakpoints` → 先用 `-break-delete` 清除该文件旧断点，再用 `-break-insert -f <file>:<line>` 设置新断点
- 维护断点 ID 映射（DAP breakpoint ID ↔ GDB breakpoint number）
- 将 GDB 返回的 `bkpt` 信息（是否 verified、实际位置）回传 VS Code
- 处理 `setFunctionBreakpoints`（如果需要）

**完成标志**：用户可以在 VS Code 编辑器行号区点击设置断点，程序运行时能正确命中。

------

###### 任务 7：`evaluate` 请求完善（返回真实 GDB 输出）

**现状**：`evaluate` 只返回固定字符串 `"Command sent to GDB"`，不返回实际结果。

**工作内容**：

- `evaluate` 请求中，用 token 关联 MI2 命令，等待 GDB 返回 `^done` 后提取真实输出
- 使 `gdbDebugSession.ts` 的 `executeGDBCommand` → `customRequest('evaluate')` 链路能拿到 ARD 命令（`ardb-get-snapshot` 等）的实际输出
- 支持 Debug Console 中用户手动输入 GDB 命令并看到结果

**完成标志**：Debug Console 中输入 `ardb-get-snapshot` 能看到 JSON 输出；Webview 面板的按钮能拿到命令真实返回值。

------

###### 任务 8：`stopped` 事件驱动自动快照 + Webview 联动优化

**现状**：面板用 500ms 轮询 + 文件读取，低效且有延迟。

**工作内容**：

- 当 `gdbAdapter.ts` 检测到 `*stopped` 事件时，主动发送 DAP `stopped` 事件
- `asyncInspectorPanel.ts` 监听 DAP `stopped` 事件 → 自动调用 `ardb-get-snapshot`（通过 evaluate）→ 直接从返回值解析 JSON（不再依赖文件轮询）
- 移除 500ms 轮询定时器
- 完善树构建逻辑：正确处理多次快照的增量更新、sync 节点去重
- 修复帧切换逻辑：点击树节点 → 使用 `stackTrace` 响应中的真实 frameId

**完成标志**：每次程序暂停时，Webview 面板自动刷新显示最新的异步执行树，点击节点能切换帧并联动变量面板。

```
任务1 (MI2解析器)
  └→ 任务2 (configurationDone + run)
       └→ 任务3 (threads + stackTrace)
       │    └→ 任务4 (scopes + variables)
       └→ 任务5 (执行控制)
```
