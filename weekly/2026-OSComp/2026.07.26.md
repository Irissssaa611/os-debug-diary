###### 1. **白名单中没有异步函数**

排查过程

- ELF 有 Future::poll 符号——nm 能看到三个 Future>::poll，白名单不应该空
- 但 GDB 输出格式不对——info functions 在 release 模式下输出如下：

```bash
root@iZ2zeaeosnumduug01ryjjZ:/home/iristseng/data/async-os# gdb-multiarch /home/iristseng/data/async-os/apps/coroutine_test/coroutine_test_riscv64-qemu-virt.elf -batch -ex "info functions" 2>/dev/null | grep -i "poll\|Future" | head -20
0xffffffc080206f36  <sync::mutex::MutexGuard<async_std::io::stdio::StdoutRaw> as core::future::future::Future>::poll
0xffffffc0802111e0  <trampoline::vsched2::Task as vsched2::interface::Task>::poll
0xffffffc080211f54  <sync::mutex::MutexGuard<alloc::collections::btree::map::BTreeMap<u64, executor::signal::SignalModule>> as core::future::future::Future>::poll
```

没有文件路径、行号、返回类型（-> core::task::poll::Poll<...>）。async-debug 的poll函数识别逻辑依赖返回类型，**所以原因是：**

**release 模式编译的 ELF 缺少完整调试信息，GDB 的 info functions 输出不包含函数签名和返回类型，导致白名单生成器无法识别异步函数。**

**解决方案**

在 release 编译时追加 -g 标志，嵌入调试信息但不改变代码优化：

```bash
make build ARCH=riscv64 BLK=n \
RUSTFLAGS="-C link-arg=-T/home/iristseng/data/async-os/linker_riscv64-qemu-virt.lds -C link-arg=-no-pie -C force-frame-pointers=yes -g"
```

  NOTE：

- 为什么不能直接用debug模式呢？因为 RISC-V JAL 指令的硬件限制（±1MB），async-os 的 trap_vector_base 用了裸汇编直接写 JAL 跳转，debug 代码膨胀后编译无法通过。要修得改汇编，改动太大了。所以选择了上面的方案。
- RUSTFLAGS 不能只传 -g，会覆盖 cargo.mk定义的默认标志，导致链接脚本丢失，必须把原有的属性 一起带上再加

###### 2. **影子栈始终为空**

断点能命中，但 snapshot 的 `path` 始终是空数组 `[]`，面板没有节点产生。

**解决方案**

添加架构检测函数，替换所有的硬编码。

###### 3. **snapshot 中有重复 CID 节点**

```json
{"thread_id": 1, "path": [{"type": "async", "cid": 1, "func": "coroutine_test::keep_name::{async_block#0}", "addr": "-0x3f7fd54330", "poll": 0, "state": 5, "file": "apps/coroutine_test/src/main.rs", "fullname": "/home/iristseng/data/async-os/apps/coroutine_test/src/main.rs", "line": 12}, {"type": "async", "cid": 1, "func": "coroutine_test::keep_name::{async_block#0}", "addr": "-0x3f7fd54330", "poll": 0, "state": 5, "file": "apps/coroutine_test/src/main.rs", "fullname": "/home/iristseng/data/async-os/apps/coroutine_test/src/main.rs", "line": 12}]}
```

同一个 CID=1 的节点在 path 中出现了两次，poll 计数也相同。这也导致异步树中有重复节点。

具体原因不是很清楚，之前path中运行完的poll函数会依靠GDB的gdb.FinishBreakpoint识别poll函数的出口然后弹出path中的节点，可能是哪个环节出错了，导致断点出口没识别到，所以我在path添加时增加一个判断：

这个poll函数之前有没有被设置过CID，还在不在path中，如果在则将它清除。因为一个poll函数要是没有运行完，是不会被再次poll的。

###### 4.  **gdb.FinishBreakpoint 在 RISC-V 上不工作**

  根据上面那个问题，我进行了相应的修改，但是发现 poll 值始终为 0。根据PollEntryBP中的实现，由于poll的值一直都不增加，分析PollEntryBP的实现，所以大概率是PopOnReturnBP(tid, cid)失败了，可能是这个GDB和Riscv适配的不是很好？不知道。

```python

# 如果创建退出断点失败了，会抛出异常导致下面不会运行
seq = _CO_POLL_SEQ.get(cid, 0) + 1  # poll 计数

```
