#### 四、论文的核心论点

所有实验和写作围绕以下论点：

> 要解释一次 Rust 异步执行，只恢复「当前在等待谁」是不够的，还必须同时恢复「本次真实控制流是怎么走到这里的」。

即需要说明三种做法单独用都不够：

- 只看 `__awaitee`（等待关系）→ 碰到 `block_on` 这种同步函数直接 poll 的情况就瞎了
- 只看调用栈（控制流）→ 看不出「谁在等谁」这个语义
- 只按函数名区分实例 → 多个同名 Future 会混成一团

所以必须三个一起上：**等待边 + 调用边 + 实例身份**。这是「混合跟踪」的含义。

#### 五、要补的实验

##### 实验一：Benchmark + 正确性

证明工具的输出是对的。

**做法**：

- 造 25–35 个小程序（每个 30–150 行），覆盖 8 类情况：纯 await 链 / async block / 手写 Future（叶子、非叶子）/ 同步包装函数 /
	多个实例共享同名 poll / 无外部 runtime / 边界情况（boxed、dyn、async closure）
- 每个程序写一份「标准答案」（ground truth）：应该有哪些实例、哪些等待边、哪些调用边、每个实例 poll 了几次
- 标准答案用临时插桩的版本生成，但论文里要强调：**工具本身不依赖插桩**，插桩只用来做评测答案

**产出**：一张表，按程序类别列出——等待边的准确率/召回率、调用边的准确率/召回率、实例识别准确率、poll 计数准确率，以及主要失败原因。

---

##### 实验二：消融实验

证明「必须混合」这件事。

**做法**：做 5 个残缺版本做对比

| 版本             | 砍掉什么         | 预期会漏掉什么                          |
| ---------------- | ---------------- | --------------------------------------- |
| 完整版           | ——               | ——                                      |
| 只保留等待边     | 调用边跟踪       | 漏掉 `block_on → Manual::poll` 这类路径 |
| 只保留调用边     | `__awaitee` 解析 | 说不出「当前在等谁」                    |
| 只按符号识别实例 | 环境指针         | 多个同名实例混成一个                    |
| 不要白名单       | 白名单过滤       | 噪声爆炸、断点数量暴涨                  |

**产出**：同一套指标 + 每个残缺版在不同类别程序上的表现对比。

##### 实验三：性能与可扩展性

**做法**：

- 写一个参数化生成器，能按参数生成不同规模的异步程序：await 链深度 D、实例数 N、每个 Future 的 poll 次数 P、无关 call-site 数 C
- 测这些：白名单生成时间 / 断点数量 / 程序运行变慢多少倍 / trace 输出多大
- 对比三种跑法：**直接跑** / **只开 GDB** / **GDB + 工具** —— 这样能把「GDB 本身的开销」和「我们工具引入的开销」分开

**产出**：几张随规模变化的曲线图 + 一张表。

##### 实验四：用户研究

**做法**（参考论文的做法，改一改）：

- **找人**：20–24 个会写 Rust 的人。要求懂 `.await` / `Poll` 的基本概念就行，不需要懂 GDB、也不需要懂编译器内部结构

- **任务**：7 个调试任务，每个都是「一个正确的程序 + 注入一个异步 bug」。每人随机做 4 个——2 个用工具、2 个不用

- **流程**：每人 1 小时，线上开会。开始前读 10 分钟教程，然后做题，每题限时 10–15 分钟，要求参与者边做边把想法说出来（think aloud），全程录屏

- **指标**：① 定位成功率 ② 定位时间 ③ 修复成功率 ④ 修复时间 

	允许用 Google / StackOverflow / AI 助手（跟参考论文一致，这样更接近真实调试）

- **正式做之前先找 4–6 人做试点**，用他们的反馈改材料。试点数据不算数

**产出**：几张统计图 + 统计检验（卡方检验、Kruskal-Wallis 检验），模仿参考论文的 Figure 11。
