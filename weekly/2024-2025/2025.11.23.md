##### 工作过程如下：

尝试重新创建新的环境，确实能够调试了，具体原因还不是很清楚。

1. **处理调试一号进程时调试会话结束的问题：**

	调试到对应位置，当调试会话结束时，code-debug server 调试终端的内容如下：

![896f84c52e4a530d76209aac2eec26b6](https://p.ipic.vip/ki7rs9.png)

可以得知崩溃的地方和原因。

2. **进行相应处理后，有出现了新的问题：**

![85534ba91443890196945974e7d29f57](https://p.ipic.vip/6ud7r6.png)

当GDB返回的`Selected thread is running`时会被判断为 error，而调试器代码会将 error 判断为很严重的错误，从而抛出异常崩溃。所以我们需要在调试器处理`parsed.token`的地方：onOutput 里拦截这个错误，把它的状态从 error 改成 done，就可以解决这个问题。

3. **处理`Selected thread is running`情况后，调试器能够成功命中一号进程的断点了，但是当一号进程执行完后，调试器自动结束了调试会话，回到调试器调试界面，终端提示：**

![截屏2025-11-23 14.07.59](https://p.ipic.vip/hbo6ek.png)

从内容中可以看到，GDB跟vscode说"Cannot execute this command while the selected thread is running."，这个其实和第二个问题是一样的，这说明GDB中有很多种关于线程在run的说法，那么为了处理这一种情况的多种说法，我们可以将在2问题中添加的那个判断的条件改成 “thread is running” ，进行宽泛的匹配。（除此之外，为了防止大小写的区别，我们也将msg的内容全部转换成小写）

4. **在解决完第三个问题后，我成功调试了第一进程，并且调试会话也没有终止，我准备启动第二个用户程序：udp.rs，并在其中打了断点，但是运行时，调试会话莫名又结束了，查看终端，结果如下：**

![截屏2025-11-23 14.33.24](https://p.ipic.vip/lqaf2d.png)

根据报错提示和相应代码，我们得知，因为前面的修改，当 GDB 返回 线程在运行的信息时，我们将其修改成了 done，然而，GDB 并没有返回`register-values` 数据包，这就导致相应的函数无法取到对应的值，从而奔溃。因此对这个函数进行相应的调整即可。

5. **解决完前面的问题，然后我想尝试进一步的调试，测试程序是matrix.rs，其中有矩阵的计算，可以来测试一下我们的调试器是否能够查看其中的矩阵的索引变量的变化，好巧不巧，就出现的问题，当我运行 matrix.rs时，调试会话就莫名结束了，查看终端提示：**

![截屏2025-11-23 15.53.28](https://p.ipic.vip/b6sqi0.png)

这个很明显就是第4个问题解决后导致的后续问题，当返回空数组后，上层函数 doAction 会觉得一定拿到一个值，并且其中最开始是没有处理空值的能力的，所以我们需要在 doAction 中每一处调用`getSomeRegisters` 或 `getStack` 的回调里，都加上空值检查。
